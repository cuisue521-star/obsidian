# 第 1 课：模型 API 封装与参数设计

> [!abstract] 本课定位
> 这是《大模型应用开发》的样板课。课程采用“问题场景—核心知识—讲师演示—微练习—独立实训—评分—补救”的完整闭环，并直接启动阶段项目 **会话式 AI 助手**。

## 一、本节学习目标

完成本课后，你能够：

1. 能画出一次模型调用从业务代码到供应商接口的数据流
2. 能用统一接口隔离业务逻辑与具体模型 SDK
3. 能区分系统指令、用户消息、调用参数和业务配置
4. 能为超时、限流、鉴权和服务异常设计明确的失败行为

## 二、学习路线

```text
观察直接调用代码的问题
        ↓
拆分业务层与模型客户端
        ↓
统一消息和配置结构
        ↓
分类处理调用异常
        ↓
替换模拟客户端进行验证
        ↓
独立完成可替换的模型调用层
```

## 四、问题场景：为什么“API 调通了”仍然不是可维护的模型应用

直接把 SDK 示例粘贴到 `main.py`，通常几分钟就能看到模型回复。但随着结构化输出、多轮会话、RAG 和工具调用加入，下面的问题会出现：

- 每个功能重复拼接请求；
- 业务代码依赖某个供应商的字段名称；
- 超时、限流和鉴权错误散落各处；
- 无法用模拟客户端做快速测试；
- 模型、参数、Prompt 和调用日志无法统一管理。

因此，本课的目标不是记住某家 SDK，而是建立稳定的模型调用边界。

## 五、核心知识一：一次模型调用包含哪些层次

### 5.1 业务层只关心任务

业务代码关心“生成课程提纲”或“分析用户问题”，不应关心 HTTP Header 和供应商响应字段。

### 5.2 客户端层负责协议差异

客户端把统一消息转换成具体请求，再把响应转换成统一结果。

### 5.3 配置层管理模型和运行参数

模型名称、超时、最大输出和重试策略应集中管理，并与 Prompt 内容分离。
## 六、核心知识二：统一消息与结果结构

### 6.1 消息至少区分角色与内容

统一使用 `role`、`content`，便于保存历史和适配不同接口。

### 6.2 返回值不应只有一段文本

除内容外，还应允许记录模型标识、结束原因、用量和请求 ID。

### 6.3 保留原始响应但不要让业务依赖它

原始响应用于排错；业务逻辑使用稳定的标准化结果。
## 七、核心知识三：参数设计不是“越随机越聪明”

### 7.1 参数必须服务任务目标

事实抽取倾向稳定，创意生成可以允许更多变化，但最终仍需测试。

### 7.2 参数属于可追踪实验条件

比较结果时要记录模型、参数、Prompt 与输入，否则无法解释差异。

### 7.3 设置输出和成本边界

最大输出、超时、重试上限都是产品行为的一部分。
## 八、核心知识四：错误要分类而不是吞掉

### 8.1 可恢复错误与不可恢复错误不同

短暂超时可能重试；无效密钥需要停止并提示配置。

### 8.2 用户提示与开发日志不同

用户看到可行动建议，日志保留技术上下文但必须脱敏。

### 8.3 模拟客户端是重要的测试工具

无需网络就能验证上层会话、界面和业务流程。

## 九、讲师演示：把直接模型调用重构成统一 ChatClient

### 演示任务

让命令行助手通过统一 `chat(messages, options)` 接口取得回复，先接模拟客户端，再替换为真实实现。
### 第一步：定义稳定输入输出

定义 Message、ChatOptions、ChatResult，使业务代码不直接读取供应商对象。
### 第二步：实现模拟客户端

固定返回可预测结果，用于验证上层调用和异常处理。
### 第三步：设计错误分类

演示鉴权错误、限流和超时分别映射为可理解的应用错误。

### 演示代码／结构示例

```python
from dataclasses import dataclass
from typing import Protocol


@dataclass
class ChatResult:
    content: str
    model: str
    finish_reason: str = "stop"


class ChatClient(Protocol):
    def chat(self, messages: list[dict], timeout: float = 30) -> ChatResult:
        ...


class FakeChatClient:
    def chat(self, messages: list[dict], timeout: float = 30) -> ChatResult:
        user_text = messages[-1]["content"]
        return ChatResult(
            content=f"模拟回复：已收到『{user_text}』",
            model="fake-model",
        )


def answer_question(client: ChatClient, question: str) -> str:
    messages = [
        {"role": "system", "content": "回答清晰，并标明不确定内容。"},
        {"role": "user", "content": question},
    ]
    return client.chat(messages, timeout=20).content
```

> [!warning] 演示要求
> 代码用于说明结构，不绑定某一厂商或框架版本。授课时要现场运行或使用等价模拟，展示正常结果、一个失败结果和验证过程。

为无密钥、限流、超时分别写一句用户提示和一条开发日志要点。

## 十一、练习参考答案

### 练习 1 参考思路

供应商响应结构泄漏到业务层；应在客户端层转换为统一结果。
### 练习 2 参考思路

前者优先可重复和严格校验，后者可允许变化；实际参数要通过测试集比较。
### 练习 3 参考思路

用户提示应告诉下一步，日志记录错误类型、请求 ID 和耗时，但不记录密钥。

> 参考答案用于核对思路，不是唯一措辞。学员必须先提交自己的分析，讲师再开放参考内容。

## 十五、本课总结

本课需要带走以下五点：

1. 业务层描述任务，客户端层处理协议差异
2. 统一消息和结果结构是后续多轮、评测与换模型的基础
3. 参数必须和任务、版本、测试结果一起记录
4. 错误分类决定重试、停止还是提示配置
5. 模拟客户端让开发和测试不依赖外部服务

## 十六、课后复习卡片

### 问：为什么不直接使用供应商返回对象？

答：它会把供应商字段扩散到业务代码，使替换、测试和升级成本变高。

### 问：所有超时都应该自动重试吗？

答：不是。要考虑重试上限、幂等性、总体预算和用户是否仍在等待。

### 问：如何验证封装是否有效？

答：替换为 FakeChatClient 或另一实现，上层业务流程无需修改。
