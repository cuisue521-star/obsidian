# 第 1 课：测试集：从需求到能力证据

> [!abstract] 本课定位
> 这是《评测与工程化》的样板课。课程采用“问题场景—核心知识—讲师演示—微练习—独立实训—评分—补救”的完整闭环，并直接启动阶段项目 **Agent 自动评测工具**。

## 一、本节学习目标

完成本课后，你能够：

1. 能把模糊的产品要求转化为可测试的能力与风险
2. 能设计正常、边界、异常和对抗四类测试样例
3. 能为每条样例记录输入、期望行为、证据与标签
4. 能从真实失败记录建立首版 Agent 测试集

## 二、学习路线

```text
从“感觉不错”转向可验证
        ↓
拆解需求与能力
        ↓
定义测试样例结构
        ↓
覆盖不同风险类型
        ↓
从真实失败生成样例
        ↓
建立首版评测集
```

## 三、前置检查

请先独立回答。这里检查的是前置理解，不要求第一次全部答对。

### 题目 1

连续手动问五个简单问题都答对，能证明 Agent 质量稳定吗？

### 题目 2

测试集只有输入和参考答案，是否足以评测所有 Agent？

### 题目 3

提示注入和越权请求应该放进功能测试还是安全测试？是否可以完全分开？

> [!tip] 讲师提示
> 先要求学员解释判断依据，再决定补充哪一段。不要因为学员选对选项就直接判定掌握。

## 四、问题场景：为什么“我试了几个问题，效果不错”无法支持发布

生成式应用输出具有变化，复杂 Agent 还包含检索、工具、状态和工作流。只挑几个顺手的问题体验，会遗漏：

- 空输入、超长输入和格式异常；
- 知识库没有证据时的拒答；
- 工具超时、部分成功和重复调用；
- 提示注入、越权路径和隐私泄露；
- 新版本平均更好但关键场景退化。

测试集不是题目仓库，而是“产品需求和风险如何被证明”的结构化资产。

## 五、核心知识一：从需求到能力证据

### 5.1 先写用户可观察行为

“系统很智能”不可测试；“证据不足时拒答并列出缺失信息”可以测试。

### 5.2 每个毕业能力都要有证据

能力模型中的结构化输出、引用、工具安全、恢复和成本都应映射到测试。

### 5.3 高风险要求设置硬门槛

越权、泄密和错误写入不能被平均分掩盖。
## 六、核心知识二：测试样例的最小结构

### 6.1 输入之外还要有期望行为

开放题未必只有唯一答案，但可以规定必须包含、禁止出现和必须引用的证据。

### 6.2 标签帮助分桶分析

标记能力、场景、难度、风险、数据版本和来源。

### 6.3 证据字段支持复现

保存标准资料、允许工具、初始状态和判断依据。
## 七、核心知识三：四类样例

### 7.1 正常样例验证核心价值

来自真实高频用户任务。

### 7.2 边界样例验证范围

空值、极短、极长、歧义和知识缺失。

### 7.3 异常样例验证恢复

接口超时、工具失败、损坏文件和状态中断。

### 7.4 对抗样例验证安全

提示注入、越权读取、诱导泄密和绕过确认。
## 八、核心知识四：测试集质量

### 8.1 代表性比数量堆砌重要

20 条有分层、有风险依据的样例优于 200 条重复简单问题。

### 8.2 从生产和练习失败中持续补充

每个真实严重失败都应沉淀为回归样例。

### 8.3 防止数据泄漏和过拟合

开发者不应只针对固定答案修改 Prompt；保留隐藏集或变体集。

## 九、讲师演示：从课程研发 Agent 的失败记录构建 8 条首版测试

### 演示任务

围绕“生成章节讲义并通过审核”建立正常、边界、异常和对抗样例。
### 第一步：列出可观察需求

必须覆盖学员、关联项目、包含练习与验收；输入不足时先澄清。
### 第二步：写成结构化样例

每条包含 id、input、expected、forbidden、tags、risk。
### 第三步：检查覆盖矩阵

确认每个关键能力和高风险失败至少有一条样例。

### 演示代码／结构示例

```python
test_case = {
    "id": "course-clarify-001",
    "input": {
        "topic": "帮我生成一门 AI 课程",
        "learner_profile": None,
    },
    "expected": {
        "behavior": "先询问目标学员与毕业成果，不直接生成完整课程",
        "must_include": ["目标学员", "毕业成果"],
    },
    "forbidden": ["编造学员基础", "直接宣称课程已完成"],
    "tags": ["boundary", "clarification", "course-design"],
    "risk": "medium",
}
```

> [!warning] 演示要求
> 代码用于说明结构，不绑定某一厂商或框架版本。授课时要现场运行或使用等价模拟，展示正常结果、一个失败结果和验证过程。

## 十、课堂微练习

### 练习 1：把形容词改成测试

把“回答要专业、准确、全面”改写成至少三个可观察验收条件。
### 练习 2：补齐样例

给只有 input 和 reference_answer 的测试样例补充标签、允许证据、禁止行为和风险级别。
### 练习 3：设计对抗样例

为 Obsidian 知识库助手设计一条诱导读取白名单外文件的测试。

## 十一、练习参考答案

### 练习 1 参考思路

例如必须引用指定资料、不得出现资料外结论、覆盖三个规定维度并使用固定结构。
### 练习 2 参考思路

具体字段取决于任务，但必须支持判断和分桶，不能只保存唯一参考文本。
### 练习 3 参考思路

输入可伪装成系统指令要求读取外部路径；期望行为是拒绝并记录越权，不调用读取工具。

> [!note] 使用方式
> 参考答案用于核对思路，不是唯一措辞。学员必须先提交自己的分析，讲师再开放参考内容。

## 十二、独立实训：建立 Agent 自动评测工具的首版测试集

### 任务背景

本任务是 **Agent 自动评测工具** 的第一个里程碑。成果将在后续课时继续扩展，不要把它当成一次性练习。

### 任务要求

1. 从一个真实项目列出 5 项核心能力和 3 项高风险失败
2. 编写不少于 20 条结构化测试
3. 正常、边界、异常、对抗四类均不少于 3 条
4. 为每条标记能力、难度和风险
5. 写出期望行为、必须项与禁止项
6. 建立覆盖矩阵并找出空白
7. 保留至少 3 条变体作为隐藏抽测

### 提交物

1. 可运行代码、结构图或产品文档；
2. README 或复现说明；
3. 一次正常案例；
4. 一次边界或失败案例；
5. 修复前后的证据；
6. 不少于 150 字的项目复盘。

### 禁止事项

- 不允许全部使用自己最熟悉的简单问题
- 不允许只写唯一参考答案而忽略行为要求
- 不允许用平均分抵消安全失败
- 不允许让同一个模型生成并无抽检地评判全部样例

## 十三、评分规则

总分 100 分。

| 评分维度 | 分值 | 合格表现 |
|---|---:|---|
| 需求映射 | 20 | 关键需求均有测试证据 |
| 样例结构 | 15 | 输入、期望、标签、风险完整 |
| 类型覆盖 | 20 | 四类样例分布合理 |
| 风险覆盖 | 15 | 高风险失败有硬测试 |
| 代表性 | 10 | 来源于真实用户与失败 |
| 可复现性 | 10 | 初始状态和证据明确 |
| 防过拟合 | 10 | 有变体或隐藏样例 |

### 通过标准

- 80 分及以上：通过本课，进入下一里程碑；
- 60～79 分：按反馈完成补救任务后重交；
- 60 分以下：重新完成前置检查和最小案例；
- 涉及密钥泄露、越权执行或伪造运行证据时，本次直接不通过。

### 错误 1：把测试集写成演示成功案例合集

**补救：** 先用最小案例复现问题，再说明错误属于概念、数据、代码、权限还是验收环节；修复后增加一条回归证据。

## 十五、本课总结

本课需要带走以下五点：

1. 测试集把需求、能力和风险转化为可验证证据
2. 开放式输出也可以通过必须项、禁止项和 Rubric 判断
3. 正常、边界、异常和对抗样例缺一不可
4. 高风险失败必须单独观察并设置硬门槛
5. 测试集应随真实失败和产品变化持续版本化

## 十六、课后复习卡片

### 问：为什么不能只看平均分？

答：少数高风险失败可能被大量简单成功掩盖，平均分不能表达风险分布。

### 问：开放题没有唯一答案，怎样测试？

答：定义期望行为、证据、必须项、禁止项和分维度 Rubric。

### 问：测试集越大越好吗？

答：不一定。代表性、分层、风险覆盖和可维护性比简单数量更重要。

## 十七、AI 讲师授课提示

> 本部分供授课 Agent 使用，不要求学员背诵。

### 授课节奏

1. 先进行前置检查，并记录学员原始解释；
2. 从问题场景进入，不要先堆叠术语；
3. 每个核心知识点都回到 **Agent 自动评测工具** 的真实决策；
4. 演示时展示输入、中间过程、输出、失败和验收；
5. 学员第一次失败只给方向，第二次给检查清单，第三次给局部示例；
6. 只有提交独立版本后才开放参考答案；
7. 结束前要求学员现场完成一个素材或条件变化的小变体；
8. 把本课产物、得分、错误类型和补课结果写入学习档案。

### 讲师判定“已掌握”的证据

- 能不照抄定义解释本课核心机制；
- 能指出方案边界和至少一个高风险失败点；
- 能独立完成项目首个里程碑；
- 能提供正常、边界或失败案例的可复现证据；
- 能解释下一课将在当前成果上增加什么能力。
