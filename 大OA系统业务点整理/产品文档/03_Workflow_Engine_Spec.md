# 中诺审批引擎核心规约 (Workflow Engine Specification) 

## 1. 核心角色定义 (Role Definitions)

系统明确划分了流程中的操作角色及其权限边界 。



| 角色                   | 权限定义                                                     |
| ---------------------- | ------------------------------------------------------------ |
| **发起人** (Initiator) | 发起审批流程，提供申请信息；可撤销、催办、作废流程           |
| **审批人** (Approver)  | 根据节点顺序审批；支持通过、驳回、拒绝、转交、加签           |
| **办结人** (Closer)    | **(可选，部分流程存在)** 在审批完成后进行最终办结确认；支持办结、驳回、转交 |
| **被抄送人** (Cc)      | 仅查看流程内容，无审批权限；由配置自动触发或主动添加         |
| **项目经理** (PM)      | 立项流程发起人自动成为项目经理；拥有编辑项目、管理干系人、查看项目下**所有**流程的权限 |
| **项目干系人**（Pc）   | 项目经理可主动添加其他人成为该项目的项目干系人，干系人和项目经理的区别是不可编辑项目内成员 |

## 2. 审批状态机 (Workflow State Machine)

系统根据流程模板配置是否包含“办结节点”，执行两套不同的状态流转逻辑。**状态流转严格遵循提供的流程图。**

### 2.1 状态定义对照表

| 状态                   | 说明                                                         |
| ---------------------- | ------------------------------------------------------------ |
| **草稿** (Draft)       | 录入保存未提交                                               |
| **审批中** (Approving) | 流程提交后，正在流转中                                       |
| **已驳回** (Rejected)  | 审批人驳回给发起人，待修改或作废                             |
| **已拒绝** (Refused)   | 审批人直接否决，**流程终止**，不可恢复                       |
| **已撤销** (Revoked)   | 发起人主动撤回流程                                           |
| **已作废** (Voided)    | 流程终止状态（由驳回后作废、或通过/办结后申请作废成功导致）  |
| **已通过** (Passed)    | (仅无办结节点) 所有审批节点通过，流程结束                    |
| **办结中** (Closing)   | (仅有办结节点) 所有审批节点通过，等待办结人处理              |
| **已办结** (Closed)    | (仅有办结节点) 办结人办结完成                                |
| **作废中** (Voiding)   | 流程达成终态（已通过/已办结）后，发起人申请作废，需审批通过才变为已作废 |



### 2.2 流程模型 A：无办结节点 (No Closing Node)

此类流程在最后一个审批人通过后，状态直接变为“已通过”。

- **正向流转：** 草稿 → 审批中 → 已通过
- **逆向/异常流转：**
  - **驳回：** 审批中 → 已驳回 → (重新提交) → 审批中
  - **拒绝：** 审批中 → 已拒绝 (终态)
  - **撤销：** 审批中 → 已撤销 (终态)
  - **作废（驳回态）：** 已驳回 → 发起人作废 → 已作废
- **事后作废流转：**
  - 已通过 → (流程发起作废) → 作废中
  - 作废中 → (作废申请通过) → 已作废
  - 作废中 → (作废申请驳回) → 已通过

### 2.3 流程模型 B：有办结节点 (With Closing Node)

此类流程在审批完成后进入“办结中”池，必须由办结人手动处理才算结束。即使审批人与办结人是同一人，也不可自动办结 。

- **正向流转：** 草稿 → 审批中 → **办结中** → (手动办结) → **已办结**

- **逆向/异常流转：**

  - **驳回：** 审批中 → 已驳回；或 **办结中 → 已驳回** (办结人也可驳回)

  - **拒绝：** 审批中 → 已拒绝

  - **撤销：** 审批中 → 已撤销 (注：办结前均可撤销 )

    

- **事后作废流转：**

  - 已办结 → (流程发起作废) → 作废中
  - 作废中 → (作废申请通过) → 已作废
  - 作废中 → (作废申请驳回) → 已办结

## 3. 审批动作交互规约 (Action Specifications)

### 3.1 发起与校验 (Initiation Rules)

- **相邻去重：** 审批人的相邻节点若为同一个人，自动合并/跳过（如 A -> A 变为 A） 。

- **非相邻不去重：** 若中间间隔他人，则不跳过（如 A -> B -> A，A 需审批两次） 。

- **办结隔离：** 办结人节点**永远不会**自动跳过，必须手动操作 。

  

### 3.2 驳回 (Reject) - 双模式

系统支持两种驳回方式，重新发起时流程编号均不变 。

| 模式                     | 逻辑行为                                               | 节点配置版本             | 适用场景             |
| ------------------------ | ------------------------------------------------------ | ------------------------ | -------------------- |
| **直送驳回** (Direct)    | 驳回至发起人，修改后**跳过中间节点**，直接回到原驳回人 | 使用**旧的**审批流配置   | 材料微调，快速审批   |
| **重新提交** (Re-submit) | 驳回至发起人，修改后**从第一节点重新开始**逐级审批     | 使用**最新的**审批流配置 | 业务实质变更，需重审 |

- **通用规则：** 驳回必须输入理由，状态变更为“已驳回” 。

### 3.3 拒绝 (Refuse)

- **终止性：** 审批人拒绝后，流程直接结束，状态变为“已拒绝” 。
- **不可逆：** 发起人无法接收待办，不可再次提交，若需处理必须新建流程 。

### 3.4 加签 (Add Node)

审批人可添加临时审批节点，处理完毕后回归原流程 。

- **前加签：** 在当前节点**之前**插入，加签人审批通过后才轮到当前人 。
- **后加签：** 在当前节点**之后**插入，当前人通过后流转给加签人 。
- **串行**：所有的多人加签，根据加签人的顺序，逐个审批。

### 3.5 转交 (Transfer)

- 当前审批人将权限移交给他人，操作后原审批人**失去**审批权限 。
- 转交后，不丢失该流程的查看权限和关联权限。

### 3.6 抄送 (Cc / Copy to)

系统支持两种抄送触发方式。

- **流程配置抄送 (System Cc):** 当流程流转到配置的特定节点时，系统自动抄送给指定人员 。
- **主动抄送 (Manual Cc):** 任何拥有流程查看权限的用户（包括发起人、审批人、已抄送人），均可主动将流程抄送给其他用户 。
- **规则：**
  - **仅查看：** 抄送人仅拥有查看权限，不可进行审批 。
  - **留痕：** 系统必须记录抄送人身份及抄送时间戳 。

### 3.7 催办 (Urge)

- **权限：** 仅发起人可操作 。

- **规则：** 催办间隔需 > 5分钟 ，不限总次数 。

- **限制：** 已终结流程（如已通过、已作废等）不可催办 。

## 4. 管理员干预机制  (Admin Intervention)

为应对人员离职、失联或长期未处理导致的流程阻塞，系统需提供管理员运维兜底能力。

### 4.1 介入权限

- **操作角色：** 主体管理员 (Subject Admin)。
- **适用场景：** 当前审批节点处理人无法履行职责（如已离职、账号被冻结、长期休假无法联系）。

### 4.2 干预逻辑 - “代处理”模式

- **待办接管：**
  - 管理员有权在后台查询“运行中”的所有流程。
  - 对于滞留在任意节点的流程，管理员可选择 **“接管待办”**。
  - **接管效果：** 该待办任务将直接出现在 **管理员自己的“工作台-待处理”** 列表中。
- **处理动作：**
  - 管理员在待办列表中打开该单据，拥有的操作权限与原审批人一致（通过、驳回、转交、拒绝）。
- **审计留痕：**
  - 系统日志必须严格区分操作主体。
  - **日志记录格式：** `[时间] [管理员ID] 代替 [原审批人ID] 执行了 [通过] 操作`。
  - 流程历史/时间轴中应标记为“管理员代办”。

## 5. 数据记录：评论 vs 备注 (Comments vs Remarks)

系统严格区分“评论”与“备注”，确保沟通的公开性与隐私性分离。

| 特性         | **评论 (Comment)**                  | **备注 (Remark)**               |
| ------------ | ----------------------------------- | ------------------------------- |
| **定义**     | 审批意见、公开沟通                  | 个人备忘录                      |
| **可见性**   | **公开** (所有可查看流程的人均可见) | **私有** (仅自己可见，互不可见) |
| **数量限制** | 无限制                              | 仅一条 (单人对单流程)           |
| **编辑权限** | **不可**编辑/删除                   | **可**编辑/删除                 |

## 6. 权限与可见性 (Permissions & Visibility)

### 6.1 项目联动

- **立项即项目经理：** 立项流程审批完成后，自动生成项目，发起人自动成为“项目经理” 。

- **项目经理权限：** 项目经理可编辑项目信息，添加/删除其他项目经理、项目干系人 。

  

### 6.2 流程可见范围

- **项目经理/干系人：** 可查看并关联该项目下**所有分期**的**全部流程** 。
- **普通流程参与者：**
  - 仅能看到**与自己相关**（审批、抄送、填写过）的流程 。
  - 虽然可在项目列表中看到项目信息，但**无法**查看项目下其他人的流程 。

## 7. 通知渠道分级 (Notification Channels)

系统根据消息的紧急程度和业务属性，区分 **短信 (SMS)** 与 **站内信 (In-App)** 两种推送渠道。

### 7.1 渠道分发原则

- **强提醒（短信）：** 仅针对 **“需要用户立即产生审批动作”** 的场景。
- **弱提醒（站内信）：** 针对 **“知情类、结果类”** 的场景。

### 7.2 全场景通知清单

| **触发场景**   | **接收对象**   | **消息类型** | **通知渠道**      | **消息模板示例**                                             |
| -------------- | -------------- | ------------ | ----------------- | ------------------------------------------------------------ |
| **轮到审批**   | 当前节点审批人 | **待办任务** | **短信 + 站内信** | 【审批】您有一条[流程名称]流程待审批，项目名称为【项目名称】，请及时处理。 |
| **轮到办结**   | 办结人         | **待办任务** | **短信 + 站内信** | 【审批】[流程名称]流程已通过，项目名称为【项目名称】，请您进行最终办结确认。 |
| **收到加签**   | 被加签人       | **待办任务** | **短信 + 站内信** | 【审批】[审批人姓名]邀请您协助审批[流程名称]流程，项目名称为【项目名称】，请及时处理。 |
| **流程被驳回** | 发起人         | 进度通知     | 站内信            | 您的[流程名称]已被[审批人]驳回，项目名称为【项目名称】，请修改后提交。 |
| **流程已通过** | 发起人         | 结果通知     | 站内信            | 恭喜，您的[流程名称]已审批通过。项目名称为【项目名称】。     |
| **流程已办结** | 发起人         | 结果通知     | 站内信            | 您的[流程名称]已完成办结归档。项目名称为【项目名称】。       |
| **流程被拒绝** | 发起人         | 结果通知     | 站内信            | 您的[流程名称]已被拒绝，流程终止。项目名称为【项目名称】。   |
| **流程被抄送** | 被抄送人       | 阅示通知     | 站内信            | [发起抄送的用户姓名]将[流程名称]抄送给您，请查阅。项目名称为【项目名称】。 |
| **收到催办**   | 当前滞留节点人 | 催办提醒     | 站内信            | [催办人姓名]正在催办[流程名称]，请尽快处理。项目名称为【项目名称】。 |



## 8. 非功能性指标 (NFR)

- **响应速度：** 单节点审批动作 ≤ 1秒 ；列表加载 ≤ 3秒 。

- **一致性：** 流程引擎必须保证状态强一致，严禁“卡流程”或“丢节点” 。
